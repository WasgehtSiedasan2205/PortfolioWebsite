FFT ocean

Own systemGLSL computeStylized
Problem

My first ocean summed a handful of Gerstner waves. It was cheap, but repetitive and flat up close — and adding more waves for detail quickly increases vertex-processing cost.

Solution

Replaced it with an FFT ocean: a few GLSL compute shaders build the spectrum and transform it into displacement and normal maps every frame — thousands of waves at a fixed cost, so fidelity and performance go up together.

Problem

Physically driven surfaces still produce artifacts — tiling, harsh normal sparkle, noisy foam — that pull the eye away from the scene.

Solution

The surface shading is deliberately stylized and cheats a little where it helps: artifacts are softened before they reach the image, so the ocean reads as calm, believable water and keeps the player immersed.

Key techniques GLSL compute shaders · ocean spectrum + FFT · displacement & normal maps · stylized surface shading · artifact suppression

SDF terrain on a voxel material grid

Own system
Problem

An SDF encodes distance to a surface, not what it's made of. Separate meshes or materials per terrain type multiply draw calls — and digging still has to reveal the right material underneath.

Solution

A parallel voxel grid stores material IDs. For every emitted triangle, the mesher repeats one ID across the CUSTOM0 values of all three vertices; a flat varying then picks the matching layer of one Texture2DArray. Every chunk is created directly on Godot's RenderingServer and shares that single material — the whole terrain renders in one draw call.

Key techniques SDF meshing · parallel voxel material grid · per-triangle IDs in CUSTOM0 · Texture2DArray · RenderingServer · triplanar mapping

Clouds as a camera compositor effect

Own systemExperiment
Problem

Volumetric-looking skies usually mean extra geometry or heavy fog volumes that fight with the ocean and terrain shading.

Solution

A CompositorEffect raymarches clouds on the GPU after transparency, straight into the camera's color buffer — no scene geometry, toggleable per camera.

Key techniques CompositorEffect · post-transparent render callback · GPU raymarching · per-camera toggle

DayZ-like movement & inertia

Own system
Problem

Default character controllers start and stop instantly. That feels like a camera on rails, not a person carrying gear — and it breaks the grounded tone a tactical shooter depends on.

Solution

An inertia system drives every movement state: speed builds up and bleeds off over time, direction changes carry momentum, and walking, jogging, and sprinting each have their own believable top speed and acceleration curve.

Key techniques Acceleration & deceleration curves · momentum on direction changes · per-state speed limits · grounded camera feel

Tarkov-style grid inventory

Own system
Problem

Shaped items, rotation, and containers inside containers: placement has to reject overlaps and out-of-bounds drops consistently — live, while dragging.

Solution

Each container owns a flat occupancy grid. Placement bounds-checks the rotated footprint, then scans only the cells it covers; nested containers keep independent grids.

Key techniques Flat occupancy grid · canonical rotated footprints · validate-before-commit placement · nested container grids

Rigidbody building system

Own system
Problem

Fully simulated building pieces jitter, drift, and become expensive once players stack dozens of them.

Solution

Pieces snap to sockets, stay dynamic while settling, and sleep at rest. Disturbances wake only the affected bodies — idle cost drops without losing physical interaction.

Key techniques Socket snapping · physics settling · sleep at rest · wake on disturbance

Project C

Planetary Rocket Sim & Trajectory Prediction

A rocket flies through the gravity of a sun and three planets. Only the rocket is simulated as a physics body; the planets move kinematically with real mass and size. What mattered was the rocket's path — predicted ahead by my own fixed-step integrator, no patched-conics shortcuts.

Role
Solo · physics & tooling
Stack
Godot 4 · GDScript 2.0
Status
Prototype

Trajectory prediction

Own system
Problem

The planets keep moving while the rocket flies, so the gravity it will feel an hour from now is not the gravity it feels now. The hard part was working out how to precompute the physics for every future timestep so the trajectory has the right shape at every point along the line.

Solution

The predictor steps forward in time: for each future step it places every planet where it will be at that moment, sums their gravity on the rocket, and integrates with the same fixed timestep as the live simulation — so the drawn path and the real flight agree.

Key techniques Per-timestep look-ahead · planet positions evaluated at future time · shared fixed-step integrator · no patched conics

Kinematic planets, physical rocket

Design decision
Problem

A full N-body simulation would make every planet react to every other body — more cost and more instability, without improving the one thing that mattered: the rocket's trajectory.

Solution

The planets move kinematically on their orbits and carry mass and size, but physics never moves them. Only the rocket is a physics body. Because every planet's position is known for any point in time, the prediction stays deterministic and cheap.

Key techniques Kinematic orbits · mass & radius per planet · single physics body · deterministic look-ahead
