Ocean shader

AdaptedOptimizedAI-assisted
Problem

The reference ocean shaders I found used incompatible wave conventions for displacement and surface orientation — hard to tune, harder to extend.

Solution

Consolidated them into one shared Gerstner wave function, with my own wave logic and AI as a sparring partner for the math. Each call returns displacement and accumulates the derivatives for the normal; four waves are summed in the vertex stage.

Key techniques Shared Gerstner parameterization · analytic derivatives · four-wave vertex displacement · normal checks at grazing angles

SDF terrain on a voxel material grid

Own system
Problem

An SDF encodes distance to a surface, not what it's made of. Separate meshes per material multiply draw calls — and digging still has to reveal the right material underneath.

Solution

A parallel voxel grid stores material IDs. For every emitted triangle, the mesher repeats one ID across the CUSTOM0 values of all three vertices; a flat varying then selects among the layers of one Texture2DArray — one shared material surface per chunk instead of one mesh per material.

Key techniques SDF meshing · parallel voxel material grid · per-triangle IDs in CUSTOM0 · Texture2DArray · triplanar mapping

Clouds as a camera compositor effect

Own systemExperiment
Problem

Volumetric-looking skies usually mean extra geometry or heavy fog volumes that fight with the ocean and terrain shading.

Solution

A CompositorEffect raymarches clouds on the GPU after transparency, straight into the camera's color buffer — no scene geometry, toggleable per camera.

Key techniques CompositorEffect · post-transparent render callback · GPU raymarching · per-camera toggle

Built: voxel data model, SDF mesher, material pipeline, compositor effect, and profiling. Adapted: base Gerstner wave equations from public shader examples; I rewrote the conventions and derivative accumulation. AI: helped derive and cross-check the wave derivatives and suggested refactors — I reviewed every change and validated it visually and with profiler captures.

Tarkov-style grid inventory

Own system
Problem

Shaped items, rotation, and containers inside containers: placement has to reject overlaps and out-of-bounds drops consistently — live, while dragging.

Solution

Each container owns a flat occupancy grid. Placement bounds-checks the rotated footprint, then scans only the cells it covers; nested containers keep independent grids.

Key techniques Flat occupancy grid · canonical rotated footprints · validate-before-commit placement · nested container grids

Rigidbody building system

Own system
Problem

Fully simulated building pieces jitter, drift and get expensive once players stack dozens of them.

Solution

Pieces snap to sockets, stay dynamic while settling, and sleep at rest. Disturbances wake only the affected bodies — idle cost drops without losing physical interaction.

Key techniques Socket snapping · physics settling · sleep at rest · wake on disturbance

Project C

Planetary Rocket Sim & N-Body Physics

A sun and three physical planets pull on each other in a full N-body simulation; the rocket flies through their evolving gravity field. Its future path is predicted by my own fixed-step integrator — no patched-conics shortcuts.

Role
Solo · physics & tooling
Stack
Godot 4 · GDScript 2.0
Status
Prototype

Trajectory prediction

Own system
Problem

With three planets and a sun all pulling at once there is no general closed-form solution for the trajectories — the player still needs to see where the rocket will go.

Solution

A ghost copy of the system is stepped forward with the same fixed-step integrator as the live simulation, so the drawn path and the real flight agree.

Key techniques Ghost-state simulation · shared fixed-step integrator · moving gravity sources · no patched conics

Stress test: launch from the sun

Testing
Problem

Normal launches hide integrator errors — gravity is gentle and steps are small compared to the forces involved.

Solution

Starting on the sun's surface is a deliberate high-acceleration regression case: predicted and live trajectories are compared over the same horizon. Close approaches, timestep variation, and long-duration runs cover the other failure modes.

Key techniques Extreme initial conditions · predicted vs. live comparison · regression scenes
