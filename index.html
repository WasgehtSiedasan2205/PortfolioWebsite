Ocean shader

AdaptedOptimizedAI-assisted
Problem

Good ocean techniques exist online, but as disconnected fragments — different conventions, redundant passes, no shared wave model.

Solution

Merged the useful parts into one Gerstner-based shader with my own wave logic, using AI as a sparring partner to unify the maths. Waves, normals and foam now come from a single evaluation per vertex.

ocean.gdshader — Gerstner wavegdshader 
// One wave: dir.xy, steepness, wavelength. Summed 4x in vertex().
vec3 gerstner(vec4 wave, vec3 p, inout vec3 tangent, inout vec3 binormal) {
    float k = TAU / wave.w;
    float c = sqrt(9.81 / k);
    vec2 d = normalize(wave.xy);
    float f = k * (dot(d, p.xz) - c * TIME);
    float a = wave.z / k;
    tangent  += vec3(-d.x * d.x * wave.z * sin(f), d.x * wave.z * cos(f), -d.x * d.y * wave.z * sin(f));
    binormal += vec3(-d.x * d.y * wave.z * sin(f), d.y * wave.z * cos(f), -d.y * d.y * wave.z * sin(f));
    return vec3(d.x * a * cos(f), a * sin(f), d.y * a * cos(f));
}

SDF terrain on a voxel material grid

Own system
Problem

Smooth SDF terrain has no notion of material. Splitting chunks by material multiplies meshes and draw calls, and digging needs to reveal the right colour underneath.

Solution

A voxel grid stores material IDs beneath the SDF. The mesher writes each vertex's material into a custom vertex channel; the shader samples one Texture2DArray by that index — one material, one draw call per chunk.

terrain.gdshader — material from vertex datagdshader 
shader_type spatial;

uniform sampler2DArray materials : source_color, filter_linear_mipmap_anisotropic;
varying flat float mat_id;   // written per vertex by the mesher (CUSTOM0)
varying vec3 w_pos;
varying vec3 w_nrm;

void vertex() {
    mat_id = CUSTOM0.x;
    w_pos = (MODEL_MATRIX * vec4(VERTEX, 1.0)).xyz;
    w_nrm = normalize((MODEL_MATRIX * vec4(NORMAL, 0.0)).xyz);
}

void fragment() {
    vec3 b = pow(abs(w_nrm), vec3(4.0));
    b /= b.x + b.y + b.z;   // triplanar weights
    ALBEDO = texture(materials, vec3(w_pos.zy * 0.25, mat_id)).rgb * b.x
           + texture(materials, vec3(w_pos.xz * 0.25, mat_id)).rgb * b.y
           + texture(materials, vec3(w_pos.xy * 0.25, mat_id)).rgb * b.z;
}

Clouds as a camera compositor effect

Own systemExperiment
Problem

Volumetric-looking skies usually mean extra geometry or heavy fog volumes that fight with the ocean and terrain shading.

Solution

A CompositorEffect raymarches clouds on the GPU after transparency, straight into the camera's colour buffer — no scene geometry, toggleable per camera.

clouds_effect.gd — render callbackGDScript 2.0 
@tool
class_name CloudsEffect
extends CompositorEffect

func _render_callback(type: int, data: RenderData) -> void:
    if type != EFFECT_CALLBACK_TYPE_POST_TRANSPARENT:
        return
    var buffers := data.get_render_scene_buffers() as RenderSceneBuffersRD
    var size := buffers.get_internal_size()
    var groups := Vector3i(ceili(size.x / 8.0), ceili(size.y / 8.0), 1)
    for view in buffers.get_view_count():
        var color := buffers.get_color_layer(view)
        _dispatch_raymarch(color, data.get_render_scene_data(), groups)

Built: voxel data model, SDF mesher, material pipeline, compositor effect, profiling. Adapted: ocean wave foundations from public shader examples. AI: used for maths review and refactoring ideas — integration, debugging and validation are mine.

Tarkov-style grid inventory

Own system
Problem

Items of different shapes, rotation and containers inside containers — naive slot lists can't answer "does this fit here?" quickly enough while dragging.

Solution

Each container is a flat occupancy grid. Placement is a bounds check plus a scan of the item's footprint; rotation just swaps width and height, so drag previews stay instant.

inventory_grid.gd — placement testGDScript 2.0 
func can_place(item: ItemData, cell: Vector2i, rotated: bool) -> bool:
    var size := Vector2i(item.size.y, item.size.x) if rotated else item.size
    if cell.x < 0 or cell.y < 0 or cell.x + size.x > width or cell.y + size.y > height:
        return false
    for y in size.y:
        for x in size.x:
            if _cells[(cell.y + y) * width + cell.x + x] != null:
                return false
    return true

Rigidbody building system

Own system
Problem

Fully simulated building pieces jitter, drift and get expensive once players stack dozens of them.

Solution

Pieces snap to sockets and settle as physics bodies, then sleep once at rest. Only disturbed structures wake up — physics where it matters, near-zero cost where it doesn't.

Trajectory prediction

Own system
Problem

With three planets and a sun all pulling at once there is no closed-form orbit — the player still needs to see where the rocket will go.

Solution

A ghost copy of the system is stepped forward with the same fixed-step integrator as the live simulation, so the drawn path and the real flight agree.

trajectory.gd — prediction loopGDScript 2.0 
func predict(start: BodyState, steps: int, dt: float) -> PackedVector3Array:
    var points := PackedVector3Array()
    points.resize(steps)
    var sim := _world.duplicate_state()   # ghost copy: planets move too
    var p := start.position
    var v := start.velocity
    for i in steps:
        var a := sim.gravity_at(p)
        v += a * dt                       # same integrator as the live sim
        p += v * dt
        sim.step(dt)
        points[i] = p
    return points

Stress test: launch from the sun

Testing
Problem

Normal launches hide integrator errors — gravity is gentle and steps are small compared to the forces involved.

Solution

Starting on the sun's surface is the worst case: extreme gravity, huge velocities. If prediction and live flight still agree there, they agree everywhere.
